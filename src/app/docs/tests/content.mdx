# Feature Tests

The `.feature` files on this page are [Gherkin specifications](https://cucumber.io/docs/gherkin/reference/){.blank}. `npx y2k-guestbook test` runs them with [Playwright](https://playwright.dev/){.blank} against your installation of the guestbook:

- A `.feature` file says what should happen.
- A step definition is the TypeScript that applies that behaviour in the browser. 

::: {.callout}
- [x] This guide assumes that you've set up the guestbook application with either [Quickstart](/docs/quickstart) or [Install via npm](/docs/install).
:::

## Install Playwright

From your Next.js app root:

```bash
npm install --save-dev @playwright/test playwright-bdd
npx playwright install chromium
```

- [`@playwright/test`](https://www.npmjs.com/package/@playwright/test){.blank} — Runs the scenarios and writes the HTML report.
- [`playwright-bdd`](https://www.npmjs.com/package/playwright-bdd){.blank} — Reads the `.feature` files and calls your step definitions.

::: {.callout}
# Quickstart installs already include  `@playwright/test` and `playwright-bdd`.

Only run `npx playwright install chromium` too to download the testing browser. 
:::

Confirm the package installations by running:

```bash
npm ls @playwright/test playwright-bdd
```

## Setup

### Test Reports

A test run writes to a Playwright report folder — open `index.html` inside to view results:

- A later run will overwrite the previous report.
- A failed scenario keeps recording in the report you can use to debug.

::: {.tabset}

# User Test Reports

The default folder is `features/reports/results/` — in this setup, we'll use this default folder for user tests.

# Admin Test Reports

`-p admin` writes `features/reports/admin/` instead of `features/reports/results/` — we'll use this custom folder for admin tests.

:::

### Support Files

[`features/support/`](https://github.com/beck-chan/y2k-guestbook/tree/main/features/support){.blank} contains files that help Playwright run tests by giving them shared context:

::: {.tabset}

# `world.ts`

[`features/support/world.ts`](https://github.com/beck-chan/y2k-guestbook/blob/main/features/support/world.ts){.blank} holds the page, the guestbook URL, and values a later step needs to read:

```typescript
export class PlaywrightWorld {
  page!: Page;
  baseUrl: string;
  guestbookPath: string;
  adminPath: string;
  postedName?: string;

  constructor() {
    this.baseUrl = String(process.env.BASE_URL ?? "http://localhost:3000").replace(/\/$/, "");
    this.guestbookPath = process.env.NEXT_PUBLIC_GUESTBOOK_PATH || "/";
    this.adminPath = process.env.NEXT_PUBLIC_GUESTBOOK_ADMIN_PATH || "/admin";
  }
}
```

::: {.callout}
# Changed Paths

If your guestbook doesn't live at the root of your domain (`/`) or the admin dashboard is not at `/admin`:

- Ensure your `NEXT_PUBLIC_GUESTBOOK_PATH` and `NEXT_PUBLIC_GUESTBOOK_ADMIN_PATH` `.env.local` variables match your custom paths so that step definitions navigate using the correct `this.guestbookPath` / `this.adminPath`.
- Keep the Gherkin wording as written (`/admin`).

:::

# `fixtures.ts`

[`features/support/fixtures.ts`](https://github.com/beck-chan/y2k-guestbook/blob/main/features/support/fixtures.ts){.blank} gives every step that same world. 

# `ui.ts`

[`features/support/ui.ts`](https://github.com/beck-chan/y2k-guestbook/blob/main/features/support/ui.ts){.blank} holds the shared locators so step definitions click visible names (`submit`, `display name`) instead of copying CSS class names.

# `seed.ts`

[`features/support/seed.ts`](https://github.com/beck-chan/y2k-guestbook/blob/main/features/support/seed.ts){.blank} writes to the database when a scenario needs rows already on the board, and resets rate limits and settings so one run does not leak into the next. 

:::

### Step Definitions

Example [`features/step_definitions/`](https://github.com/beck-chan/y2k-guestbook/tree/main/features/step_definitions){.blank} map each `Given` / `When` / `Then` to clicks in the browser, covering the basic functionality of the guestbook, aligning with the [Gherkin `.feature` files](#gherkin-feature-files) below.

You will need to [write step definitions](#write-additional-tests) for any additional functionality you opt into (notifications, analytics) or any other features that you add.

### Run `.feature` Tests

::: {.tabset}

# Run User Tests

These tests do not require any admin authentication, so they can be run without any additional setup.

1. Start the guestbook preview server: `npm run dev`

2. In a second terminal at the app root, call:

  ::: {.tabset}


  # To Run One Test 

  To run a specific test in a feature file, append the `--name` flag naming a Scenario. For example:


  ```bash
  # Writes to features/reports/results/index.html
  npx y2k-guestbook test features/features/guestbook/guestbook-comments.feature --name "User submits a valid comment"
  ```

  # Run a Set Tests

  For a specific set of tests under one Rule, append the  `--tags @example-rule-name` flag:

  ```bash
  # Writes to features/reports/results/index.html
  npx y2k-guestbook test features/features/guestbook/guestbook-comments.feature --tags @submit-comments
  ```

  # Run Suite of Tests

  For example, the full `guestbook-nav.feature` file:

  ```bash
  # Writes to features/reports/results/index.html
  npx y2k-guestbook test features/features/guestbook/guestbook-nav.feature
  ```


  # To Run All Tests

  ```bash
  # Writes to features/reports/results/index.html
  npx y2k-guestbook test features/features/guestbook
  ```

  :::

# Run Admin Tests

::: {.callout}
# Playwright cannot finish Google's login screen by itself. 

- Run these scenarios with the browser visible and sign in with your authorized admin user in order to test the scenarios under [Admin Dashboard](#admin-dashboard). 
- These runs are configured to use Chrome (not Chromium) otherwise your admin dashboard OAuth 2.0 client will block the request, so make sure you have Chrome installed.

:::

1. Start the guestbook preview server: `npm run dev`

2. In a second terminal at the app root, call:

3. You'll need to run Chrome in debugging mode. Close all Chrome windows you might have open first, then call (replace the `--user-data-dir` paths with your own):

  ::: {.tabset} 

  # On Windows

  ```bash
  "/c/Program Files/Google/Chrome/Application/chrome.exe" --remote-debugging-port=9222 --remote-allow-origins=* --user-data-dir="C:/Users/username/path/to/your-app/features/support/.auth/chrome-debug"
  ```

  # On macOS
  ```bash
  open -a "Google Chrome" --args --remote-debugging-port=9222 --remote-allow-origins=* --user-data-dir="~/path/to/your-app/features/support/.auth/chrome-debug"
  ```

  :::

  Confirm that debugging is enabled by using the open Chrome window to view: [http://127.0.0.1:9222/json/version](http://127.0.0.1:9222/json/version ){.blank}

4. Leave the Chrome window that opens up and in a third terminal call:

  ::: {.tabset}

  # Run One Test

  To run a specific test in a feature file, append the `--name` flag naming a Scenario. For example:

  ```bash
  # Writes to features/reports/admin/index.html
  HEADED=1 npx y2k-guestbook test -p admin features/features/admin/admin-settings.feature --name "Admin can update the guestbook title"
  ```

  # Run a Set Tests

  For a specific set of tests under one Rule, append the `--tags @example-rule-name` flag:

  ```bash
  # Writes to features/reports/admin/index.html
  HEADED=1 npx y2k-guestbook test -p admin features/features/admin/admin-nav.feature --tags @mobile-menu
  ```

  # Run Suite of Tests

  For example, the full `admin-nav.feature` file:

  ```bash
  # Writes to features/reports/admin/index.html
  HEADED=1 npx y2k-guestbook test -p admin features/features/admin/admin-nav.feature
  ```

  # Run All Tests

  ```bash
  # Writes to features/reports/admin/index.html
  HEADED=1 npx y2k-guestbook test -p admin features/features/admin
  ```

  :::

3. When Google's login screen appears, sign in with your allow-listed admin user. 

  For gated (unauthorized) scenarios, sign in with a Google account that is not an administrator.

:::

## Write Additional Tests

If a `Given` / `When` / `Then` already has a matching function, Playwright runs that function. The terminal prints a stub for a Gherkin line with no match. Create `features/step_definitions/your-steps.ts`, paste the stub, and add this import:

```typescript
import { Given, When, Then } from "y2k-guestbook/testing";

Given("a user is on the guestbook page", async function () {
  await this.page.goto(this.guestbookUrl());
});
```

Fill in the body with the appropriate code to execute the step. Instruction should be written the way a human user would find things on the page — for example, reference the `submit` button, the `display name` field, the `prev` / `next` links, and not CSS class names or code.

- It doesn't matter what the file is called, as long as it's in the `features/step_definitions/` directory and has the `.ts` extension.
- Stash values you will need later on the World object (for example `this.postedName`).


::: {.callout}
# Example Functions

| Function | Description |
| --- | --- |
| `this.page.goto(url)` | Open a page. Build the URL from `this.baseUrl` so the same steps work on `localhost` and a deployed site. |
| `this.page.getByLabel("display name").fill(text)` | Type into a field by its visible name (`display name`). |
| `this.page.getByRole("button", { name: "submit" }).click()` | Role is the kind of control (`button`, `link`). Name is the text on it (`submit`, `prev`, `next`). |
| `this.page.locator('textarea[name="comment"]').fill(text)` | Reach a field that has no visible label. Use name or role over CSS class names. |
| `locator.waitFor()` and `assert.match(await locator.innerText(), /…/)` | Wait until the result is on the page, then fail the step if the visible text does not match. |
| `this.page.setViewportSize({ width, height })` | Shrink the window *before* `goto` when the Gherkin line says *on mobile*. |

:::
