# Enable Notifications

::: {.callout}
- [x] This guide assumes that you've set up the guestbook application with either [Quickstart](/docs/quickstart) or [Install via npm](/docs/install).

:::


When notifications are enabled, emails are sent for:

| Event | Recipients |
| --- | --- |
| New email added/invited to admin allow-list ("Admin list") | The new address, and existing admin list |
| Email removed from the admin allow-list | The removed address, and existing admin list |
| Comment submitted | Admin list |
| Admin edits or deletes a comment | Admin list |
| Guestbook settings saved | Admin list |
| Invited admin completes sign-in for the first time | The new user, and existing admin list |

## Create Webhook Secret

[Supabase Edge Functions](https://supabase.com/docs/guides/functions){.blank} check a shared secret instead of a user JSON Web Token (JWT). 

We'll first generate a shared secret that will be used with our Supabase database webhooks. 

1. Use a secure password generator like [Bitwarden's password generator](https://bitwarden.com/password-generator/){.blank}:

    - Choose **Password** and not Passphrase.
    - Set the **Characters** length to `32` or longer.
    - Leave **A–Z**, **a–z**, and **0–9** on, and keep !@#$%^&* off so you can paste the value into `npx supabase secrets set` without quoting.

2. Copy the generated password. Hang on to this — we'll need to store this as Supabase secret when we connect Google OAuth 2.0 to Supabase under `NOTIFY_WEBHOOK_SECRET`:

    ```bash
    NOTIFY_WEBHOOK_SECRET=<your-webhook-secret>
    ```

::: {.callout}
# Treat your webhook secret like a password.

Anyone who gets a hold of your `NOTIFY_WEBHOOK_SECRET` can send emails as you. If it's compromised, generate a new one and update the Supabase secret and your webhooks.
:::


## Create Gmail Google Cloud Project

::: {.callout}
# Notifications are send out from your personal Gmail, not a branded domain.

- The [Supabase Edge Functions](https://supabase.com/docs/guides/functions){.blank} call the Gmail API over HTTPS, and recipients will be shown the address set in `GMAIL_USER`.
- Please note that Gmail has a low daily send limit for this type of setup, around ~100–500/day.
:::

As sending emails requires more sensitive scopes, which may delay the approval of your OAuth client if you intend to [publish the OAuth client for the admin authentication](/docs/admin#publish-your-google-oauth-client) to the general public, let's create a new project for notifications.

Log in to your [Google Cloud](https://console.cloud.google.com/){.blank} console:

::: {.tabset}

# 1. Enable Gmail API

a. [Create a new Google Cloud project](https://developers.google.com/workspace/guides/create-project){.blank}.

b. Make sure to select the project you just created by clicking **Select your project** (or the name of the guestbook project, if that is what you have currently selected).

c. In the left sidebar, click **APIs & Services**, then **Library**.

d. Under Google Workspace, select **Gmail API**.

e. Click **Enable**.

# 2. Create Client

a. In the left sidebar, click **APIs & Services**, then select **OAuth consent screen**.

b. In OAuth Overview, click **Get started**.

c. Configure your project, then click **Create**. For example, enter your:

    - App Information
    - Audience (for personal Google accounts, select `External`)
    - Contact Information
    - Finish (to agree to the Google API Services: User Data Policy)

d. Click **Create**.

e. In the left sidebar, click **APIs & Services**, then select **Credentials**.

f. Click **+ Create credentials**, then select **OAuth client ID**.

g. In the **Application type** drop-down, select `Web application`.  

h. Give your application a **Name**.

i. Click **Create**.

j. On the OAuth client created popup, copy the **Client ID** and **Client secret** to your clipboard. Hang on to these — we'll need to store these as Supabase secrets in the next section under `GMAIL_CLIENT_ID` and `GMAIL_CLIENT_SECRET`:

    ```bash
    GMAIL_CLIENT_ID=<your-client-id>.apps.googleusercontent.com
    GMAIL_CLIENT_SECRET=<your-client-secret>
    ```


    ::: {.callout}
    Click **Download JSON** to save your OAuth client credentials to a file as a backup.
    :::

# 3. Create Refresh Token

a. Open [OAuth 2.0 Playground](https://developers.google.com/oauthplayground/){.blank}.

b. Click the <DocsGear /> icon (OAuth 2.0 configuration). 

c. Check the **Use your own OAuth credentials** checkbox. 

d. Paste in your `GMAIL_CLIENT_ID` and `GMAIL_CLIENT_SECRET` from the OAuth 2.0 client you just created.

e. Click **Close**.

f. From the scope list left sidebar, open **Gmail API v1** and select `https://www.googleapis.com/auth/gmail.send`. 

h. Click **Authorize APIs**.

i. Sign in as the user that is connected to the OAuth 2.0 client you just created to allow access.

j. Click **Exchange authorization code for tokens**, then copy the **Refresh token**. 

    Hang on to this — we'll need to store these as Supabase secrets in the next section under `GMAIL_REFRESH_TOKEN`:

    ```bash
    GMAIL_REFRESH_TOKEN=<your-refresh-token>
    ```

::: {.callout}
# Treat your refresh token like a password. 

If Google revokes the refresh token, you'll need to create a new token and update the Supabase secret if mail stops.

:::

:::

## Deploy Edge Functions

Let's deploy the edge functions in [`supabase/functions`](https://github.com/beck-chan/y2k-guestbook/blob/main/supabase/functions/README.md){.blank} to Supabase that will handle your notifications.

::: {.callout}
# You'll need your Supabase Project ID snagged from your `NEXT_PUBLIC_SUPABASE_URL`: `https://<your-database-url>.supabase.co`.

:::

1. From your guestbook project root, call:

    ```bash
    # Make sure you're logged in
    npx supabase login
    npx supabase functions deploy notify-admins on-user-created --project-ref <your-database-url>
    ```

2. Set the following Supabase secrets:

    ```bash
    npx supabase secrets set --project-ref <your-database-url> GMAIL_USER=you@gmail.com
    npx supabase secrets set --project-ref <your-database-url> GMAIL_CLIENT_ID=<your-client-id>.apps.googleusercontent.com
    npx supabase secrets set --project-ref <your-database-url> GMAIL_CLIENT_SECRET=<your-client-secret>
    npx supabase secrets set --project-ref <your-database-url> GMAIL_REFRESH_TOKEN=<your-refresh-token>
    # Use localhost:3000 for local previews, your deployed site URL in production
    npx supabase secrets set --project-ref <your-database-url> SITE_URL=https://<your-project-url>.vercel.app
    npx supabase secrets set --project-ref <your-database-url> NOTIFY_WEBHOOK_SECRET=<your-webhook-secret>
    npx supabase secrets set --project-ref <your-database-url> FLAG_NOTIF=false
    ```

    If your admin dashboard is not at `/admin`, also set your `GUESTBOOK_ADMIN_PATH`.

## Configuring Webhooks

### Configure Database Webhooks

Within Supabase, select **Database** from the left sidebar, then click **Webhooks**:

::: {.tabset}

# 1. Create the notify-admins hook

a. Click **Create a new hook**.

b. Give the hook a **Name**. For example: `notify-admins`.

c. For **Table**, you will add one hook per table (or enable each table/event below on this hook, depending on the Dashboard).

d. Set **HTTP Request** to:

    - **Method:** `POST`
    - **URL:** `https://<your-database-url>.supabase.co/functions/v1/notify-admins`

    Replace `<your-database-url>` with the ref in your `NEXT_PUBLIC_SUPABASE_URL`.

e. Under **HTTP Headers**, add:

    | Name | Value |
    | --- | --- |
    | `x-notify-webhook-secret` | The same string as `NOTIFY_WEBHOOK_SECRET` |
    | `Content-Type` | `application/json` |

f. Click **Create webhook**.

# 2. Tables and events

Create hooks (or extra table events) so `notify-admins` receives:

| Table | Events |
| --- | --- |
| `public.admin_allowlist` | INSERT, DELETE |
| `public.comments` | INSERT, UPDATE, DELETE |
| `public.guestbook_settings` | UPDATE |

Do **not** enable UPDATE on `admin_allowlist`. Re-running `npm run allow-admin` for an existing address must not send mail.

:::

### After User Created Hook

This emails the new admin and the rest of the allowlist the first time an allowlisted Google account is created in Auth. Later logins do not send mail.

a. Within Supabase, select **Authentication** from the left sidebar, then click **Hooks**.

b. Click **Add hook**, then select **After User Created**:

    - For **Hook type**, select `HTTPS`.
    - For **URL**, enter `https://<your-database-url>.supabase.co/functions/v1/on-user-created`.

c. Set the hook secret / Authorization bearer token to the same `NOTIFY_WEBHOOK_SECRET` value.

d. Click **Create hook**.

::: {.callout}
# Keep the existing Before User Created Postgres hook.

That hook (`hook_before_user_created`) still blocks Google accounts that are not on the allowlist. After User Created only runs when a new Auth user is actually created.
:::

## Enable Notifications

`FLAG_NOTIF` must be on in **two** places. Next.js env vars never reach Edge Functions.

In `.env.local` (for local development) or your Vercel environment variables (for cloud deployment):

1. Toggle **`FLAG_NOTIF=`** to `true`.

    ```bash
    FLAG_NOTIF=true
    ```

2. On the same Supabase project, turn the send gate on:

    ```bash
    npx supabase secrets set FLAG_NOTIF=true
    ```

::: {.callout}
# `.env.local` / Vercel `FLAG_NOTIF=true` alone does not send mail.

The Edge Function reads the **Supabase secret**. Set both so the Next flag and the mailer agree. Leave the secret `false` until the Gmail API refresh token and the webhooks are ready.
:::

For cloud deployment, add `FLAG_NOTIF` as a Vercel environment variable (`true` / `false`) the same way you set `FLAG_COUNTER`. Restart or redeploy after changing Next flags.

## Test Notifications

With `FLAG_NOTIF=true` as a Supabase secret and the Gmail refresh token working:

1. Run `npm run allow-admin -- someone@gmail.com` for an address that is not already listed. That inbox, and other allowlisted inboxes, should receive mail. Run the same command again for that address — no second mail.

2. Run `npm run delete-admin -- someone@gmail.com`. The removed address and remaining admins should receive mail.

3. Submit a comment on the public guestbook. Allowlisted inboxes should receive mail. Mark the comment read in `/admin` — no mail. Edit or delete it — mail.

4. Save guestbook settings. Allowlisted inboxes should receive a short list of changed fields.

5. Sign in with Google using a newly allowlisted account that has never had an Auth user. That address and other admins should receive mail. Sign out and in again — no mail.

Inserting a comment row in the Supabase **SQL Editor** should still send mail. That confirms the webhook, not the Next action.

::: {.callout}
# Gmail does not dedupe retries.

If a Database Webhook retries, the same event can send twice. Re-running `allow-admin` for an address that is already listed still must not mail (that is an UPDATE, and the function skips it).
:::
