# Enable Notifications

<Setup />

When notifications are enabled, emails are sent for:

| Event | Recipients |
| --- | --- |
| New email added/invited to admin allow-list ("Admin list") | The new address, and existing admin list |
| Email removed from the admin allow-list | The removed address, and existing admin list |
| Comment submitted | Admin list |
| Admin edits or deletes a comment | Admin list |
| Guestbook settings saved | Admin list |
| Invited admin completes sign-in for the first time | The new user, and existing admin list |

## Gmail Setup

::: {.callout}
# Mail is sent as your Gmail, not a branded domain.

The Edge Functions call the **Gmail API** over HTTPS (the same pattern as any HTTP mailer). Recipients see the mailbox in `GMAIL_USER`.

- This is **not** a Gmail App Password or SMTP. App Passwords only work on SMTP; Edge Functions cannot reliably use Gmail’s SMTP ports.
- Personal Gmail has a low daily send cap. That is enough for a small admin list.
- Google can revoke the OAuth refresh token. Create a new token and update the Supabase secret if mail stops.
- Do **not** add `gmail.send` to guestbook admin Google sign-in. This OAuth client is only for sending notifications.
- `FLAG_NOTIF` must be `true` as a **Supabase secret** before anything sends.
:::

### Retrieve Gmail Variables

Use the [Google Cloud](https://console.cloud.google.com/){.blank} project you already use for Sign in with Google, or a new project. Keep the existing admin-login OAuth client unchanged.

::: {.tabset}

# 1. Enable Gmail API

a. In Google Cloud, select your project.

b. In the left sidebar, click **APIs & Services**, then **Library**.

c. Search for **Gmail API**, open it, and click **Enable**.

d. You will store the sending address as the Supabase secret `GMAIL_USER` (the Gmail that should appear as From):

    ```bash
    GMAIL_USER=you@gmail.com
    ```

# 2. Create an OAuth Client

a. In **APIs & Services**, click **OAuth consent screen**.

    - User type **External** is fine for a personal mailbox.
    - Publishing status **Testing** is enough. Under **Test users**, add the same Gmail as `GMAIL_USER`.

b. In **APIs & Services**, click **Credentials**, then **+ Create credentials** → **OAuth client ID**.

c. Application type **Desktop app** is fine. Name it for example `Guestbook notifications`.

d. Copy the **Client ID** and **Client secret**. You will store them as Supabase secrets:

    ```bash
    GMAIL_CLIENT_ID=<your-client-id>.apps.googleusercontent.com
    GMAIL_CLIENT_SECRET=<your-client-secret>
    ```

::: {.callout}
# Do not reuse the Supabase Google provider client for `gmail.send`.

Admin login stays on its current scopes. Notifications use this separate client.
:::

# 3. Create a Refresh Token

a. Open [OAuth 2.0 Playground](https://developers.google.com/oauthplayground/){.blank}.

b. Click the gear (OAuth 2.0 configuration). Check **Use your own OAuth credentials**. Paste `GMAIL_CLIENT_ID` and `GMAIL_CLIENT_SECRET`.

c. In the scope list, find **Gmail API v1** and select `https://www.googleapis.com/auth/gmail.send`. Click **Authorize APIs**.

d. Sign in as `GMAIL_USER` (the test user). Allow access.

e. Click **Exchange authorization code for tokens**. Copy **Refresh token**. You will store it as:

    ```bash
    GMAIL_REFRESH_TOKEN=<your-refresh-token>
    ```

Treat the refresh token like a password. If Google revokes it, repeat this tab and update the secret.

:::

## Supabase Setup

Functions live in [`supabase/functions`](https://github.com/beck-chan/y2k-guestbook/blob/main/supabase/functions/README.md){.blank} on the guestbook repo you deploy. `notify-admins` handles table changes. `on-user-created` handles first Google signup.

### Deploy Edge Functions

From your guestbook project root, after `npx supabase link` to *your* project:

```bash
npx supabase functions deploy notify-admins on-user-created
```

::: {.callout}
# These functions set `verify_jwt = false`.

Database Webhooks and Auth hooks do not send a user JWT. The functions check `NOTIFY_WEBHOOK_SECRET` instead.
:::

### Set Function Secrets

Secrets are set on the **Supabase project**, not in Next `.env.local` (except `FLAG_NOTIF`, which you set in both places later).

a. Generate a long random string for the webhook secret.

b. In a terminal, from your guestbook project:

    ```bash
    npx supabase secrets set GMAIL_USER=you@gmail.com
    npx supabase secrets set GMAIL_CLIENT_ID=<your-client-id>.apps.googleusercontent.com
    npx supabase secrets set GMAIL_CLIENT_SECRET=<your-client-secret>
    npx supabase secrets set GMAIL_REFRESH_TOKEN=<your-refresh-token>
    npx supabase secrets set SITE_URL=https://<your-project-url>.vercel.app
    npx supabase secrets set NOTIFY_WEBHOOK_SECRET=<your-webhook-secret>
    npx supabase secrets set FLAG_NOTIF=false
    ```

c. For local previews, `SITE_URL` can be `http://localhost:3000`. Use your deployed origin in production.

d. (Optional) If the admin dashboard is not at `/admin`, also set `GUESTBOOK_ADMIN_PATH` to that path (no trailing slash).

`SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are provided to Edge Functions automatically.

### Database Webhooks

Within Supabase, select **Database** from the left sidebar, then click **Webhooks**:

::: {.tabset}

# 1. Create the notify-admins hook

a. Click **Create a new hook**.

b. Give the hook a **Name**. For example: `notify-admins`.

c. For **Table**, you will add one hook per table (or enable each table/event below on this hook, depending on the Dashboard).

d. Set **HTTP Request** to:

    - **Method:** `POST`
    - **URL:** `https://<your-project-ref>.supabase.co/functions/v1/notify-admins`

    Replace `<your-project-ref>` with the ref in your `NEXT_PUBLIC_SUPABASE_URL`.

e. Under **HTTP Headers**, add:

    | Name | Value |
    | --- | --- |
    | `x-notify-webhook-secret` | The same string as `NOTIFY_WEBHOOK_SECRET` |
    | `Content-Type` | `application/json` |

f. Click **Create webhook**.

# 2. Tables and events

Create hooks (or extra table events) so `notify-admins` receives:

| Table | Events |
| --- | --- |
| `public.admin_allowlist` | INSERT, DELETE |
| `public.comments` | INSERT, UPDATE, DELETE |
| `public.guestbook_settings` | UPDATE |

Do **not** enable UPDATE on `admin_allowlist`. Re-running `npm run allow-admin` for an existing address must not send mail.

:::

### After User Created Hook

This emails the new admin and the rest of the allowlist the first time an allowlisted Google account is created in Auth. Later logins do not send mail.

a. Within Supabase, select **Authentication** from the left sidebar, then click **Hooks**.

b. Click **Add hook**, then select **After User Created**:

    - For **Hook type**, select `HTTPS`.
    - For **URL**, enter `https://<your-project-ref>.supabase.co/functions/v1/on-user-created`.

c. Set the hook secret / Authorization bearer token to the same `NOTIFY_WEBHOOK_SECRET` value.

d. Click **Create hook**.

::: {.callout}
# Keep the existing Before User Created Postgres hook.

That hook (`hook_before_user_created`) still blocks Google accounts that are not on the allowlist. After User Created only runs when a new Auth user is actually created.
:::

## Enable Notifications

`FLAG_NOTIF` must be on in **two** places. Next.js env vars never reach Edge Functions.

In `.env.local` (for local development) or your Vercel environment variables (for cloud deployment):

1. Toggle **`FLAG_NOTIF=`** to `true`.

    ```bash
    FLAG_NOTIF=true
    ```

2. On the same Supabase project, turn the send gate on:

    ```bash
    npx supabase secrets set FLAG_NOTIF=true
    ```

::: {.callout}
# `.env.local` / Vercel `FLAG_NOTIF=true` alone does not send mail.

The Edge Function reads the **Supabase secret**. Set both so the Next flag and the mailer agree. Leave the secret `false` until the Gmail API refresh token and the webhooks are ready.
:::

For cloud deployment, add `FLAG_NOTIF` as a Vercel environment variable (`true` / `false`) the same way you set `FLAG_COUNTER`. Restart or redeploy after changing Next flags.

## Test Notifications

With `FLAG_NOTIF=true` as a Supabase secret and the Gmail refresh token working:

1. Run `npm run allow-admin -- someone@gmail.com` for an address that is not already listed. That inbox, and other allowlisted inboxes, should receive mail. Run the same command again for that address — no second mail.

2. Run `npm run delete-admin -- someone@gmail.com`. The removed address and remaining admins should receive mail.

3. Submit a comment on the public guestbook. Allowlisted inboxes should receive mail. Mark the comment read in `/admin` — no mail. Edit or delete it — mail.

4. Save guestbook settings. Allowlisted inboxes should receive a short list of changed fields.

5. Sign in with Google using a newly allowlisted account that has never had an Auth user. That address and other admins should receive mail. Sign out and in again — no mail.

Inserting a comment row in the Supabase **SQL Editor** should still send mail. That confirms the webhook, not the Next action.

::: {.callout}
# Gmail does not dedupe retries.

If a Database Webhook retries, the same event can send twice. Re-running `allow-admin` for an address that is already listed still must not mail (that is an UPDATE, and the function skips it).
:::
